# AGENTS.md — data-access-api (OMOP Queries)

## Service Overview

FastAPI service for querying the OMOP Common Data Model database. Receives cohort query requests from trust-api, translates them to SQL, executes against omop-db, and returns results.

## Key Patterns

- Connects to omop-db (PostgreSQL port 5432) on the trust network
- Receives internal requests from trust-api (all `/cohort` endpoints) and from imaging-api (`/cohort/accession-ids`); not directly exposed
- Every internal caller authenticates with the per-trust `TRUST_INTERNAL_SERVICE_KEY` header (see [`trust/AGENTS.md`](../AGENTS.md#trust-internal-service-authentication)). `/health` stays unauthenticated. The cohort router is **split by privilege** (`utils/internal_auth.py`): the read router (`/cohort` statistics, `/cohort/dataframe`, `/cohort/accession-ids`) requires the trust-internal key; the write router (`/cohort/snapshot`, `/cohort/snapshot/delete`) requires that **plus** cohort-admin — `authenticate_cohort_admin`, proof of possessing `AES_KEY_BASE64` (SHA-256 of the key, constant-time compared). fl-client holds the trust-internal key (for its reads) but no AES key, so it cannot define/destroy a project's frozen cohort (FLIP#857). A valid trust-internal key without the proof → 403
- OMOP CDM query translation layer
- `services/cohort.py::validate_query` is the **authority** on cohort-query safety: one parse-validate-emit pass that returns the query re-emitted from the AST it checked. Pass that return value to the engine, never the caller's raw string. The hub runs its own pre-check, but it is fast-feedback only and deliberately weaker — never relax a rule here on the assumption the hub filtered first, and do not mirror trust-local rules onto the hub. See [`README.md`](README.md#cohort-query-validation)
- Both row-level routes — `/cohort/dataframe` (FL training data) and `/cohort/accession-ids` (the accession list that decides whose imaging is pulled into XNAT) — are gated on `COHORT_QUERY_THRESHOLD` and share one fixed refusal string, so a below-threshold cohort is indistinguishable from an empty one and the refusal cannot act as a row-count oracle. The trust enforces this itself; the hub's staging guard is not relied on
- **Row-level routes serve ONLY the approved cohort's frozen membership (FLIP#857)** — what `POST /cohort/snapshot` persists at project approval (`services/cohort_snapshot.py`: one `membership.json` per project UUID under `COHORT_SNAPSHOT_DIR`, a dedicated bind mount — the SQL of record plus the distinct `person_id` / `accession_id` values, never clinical values; atomic write-once rename — a frozen membership is never replaced, and a record present but unreadable is a 500 on a freeze, never written over; no TTL). The caller-supplied SQL on those routes is **ignored** (hash-compared and logged on drift) — this closes the audit finding that researcher FL code could execute arbitrary SQL under a project id. `/cohort/dataframe` re-runs the query of record live and uncached, keeping a row only when every frozen id column it has a value in holds a member, and at least one does (can shrink, never grow; a frozen column the query no longer projects matches nothing). `/cohort/accession-ids` never runs the cohort SQL: frozen accessions ∩ `omop.image_occurrence` (`keep_imaging_accessions`). Both re-count distinct subjects, uncached, over what they would release (a tabular project's empty accession list is gated on the approval-time count) and gate on the policy decision's `effective_threshold`. A project with no membership is refused (fail-closed; fixed generic detail); a cohort frozen without `accession_id` serves an **empty** accession list (tabular project). A cohort exposing neither `person_id` nor `accession_id` is refused at creation with a 400 naming the column. The two write routes (`/cohort/snapshot`, `/cohort/snapshot/delete`) are gated on cohort-admin (AES-possession) beyond the trust-internal key — researcher FL code cannot reach them. `/cohort/snapshot/delete` is the (not-yet-called) FLIP#997 teardown hook
- `COHORT_QUERY_THRESHOLD` is the trust's own disclosure floor (default 10), set per trust in its kit file. It is a `PositiveInt`: `0` would disable both row-level gates (a subject count is never below `0`) *and* the statistics suppression at once, so a non-positive value is rejected at import and the service refuses to start rather than run with no floor. Its default lives in one place — the module-level `DEFAULT_COHORT_QUERY_THRESHOLD`, read by both the field default and the empty-string coercion validator; do not re-inline the literal. Requiring the value to be at least the shipped 10 rather than merely positive is FLIP#870. Any new non-`str` setting needs its own empty-string coercion validator: the service Makefile's `export $(shell sed 's/=.*//' $(KIT_ENV_FILE))` strips values from commented lines too, so a commented-out entry arrives as `""` and pydantic rejects it at import
