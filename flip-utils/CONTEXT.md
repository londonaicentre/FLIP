# flip-utils

The NVIDIA FLARE federated learning base library for the FLIP ecosystem. This project
provides pip-installable Python packages (`flip-utils`), reusable NVFLARE components,
Docker services for FL networks, and tutorial applications for medical imaging.

## Language

**Client API**:
The modern NVFlare API for client-side federated learning, using `flare.init()`,
`flare.receive()`, and `flare.send()` instead of the legacy Executor/Controller pattern.
_Avoid_: Executor, Controller (when referring to the old pattern)

**FedAvgRecipe**:
A PyTorch-specific recipe class (`nvflare.app_opt.pt.recipes.fedavg.FedAvgRecipe`) that
configures a complete FedAvg job with ScriptRunner, model persistor, and optional early
stopping — replacing manual `config.json` setup.
_Avoid_: config.json, ScatterAndGather

**FLUNet**:
A thin wrapper around `monai.networks.nets.UNet` that stores constructor parameters as
instance attributes so the PyTorch model serialiser can reconstruct it from a config dict.
_Avoid_: get_model() function, plain UNet (in job context)

**MonaiAlgo**:
A MONAI `fl.client` class that wraps MONAI bundle configs for federated learning, exposing the
platform-neutral `ClientAlgo` contract (`train`/`get_weights`/`evaluate`, exchanging
`ExchangeObject`). Internally it builds a `ConfigWorkflow`, so it is *not* what gives a bundle its
native training loop; that is `ConfigWorkflow`'s job, reachable without it.
Not used in **hand-written apps or tutorials**: there we drive the Client API directly. Whether the
MONAI bundle on-ramp uses `MonaiAlgo` or drives `ConfigWorkflow` under a FLIP-owned round loop is
settled by the adapter spike (FLIP#1107, recorded as ADR-0006); backend-neutrality, `MonaiAlgo`'s
main draw, buys nothing now that the on-ramp is NVFLARE-only (ADR-0005).
_Avoid_: "we don't use MONAI bundles" as a blanket statement: true of the hand-written path,
false of the bundle on-ramp, which exists precisely to consume them.

**Training bundle** vs **inference bundle**:
Two opposite things both called "bundle" in this repo. An **inference bundle** is what
`flip/export/` *produces* from a finished run (TorchScript carrying `inference.json` and
`metadata.json`, or the directory form with plain weights), the shape `MonaiBundleInferenceOperator`
consumes on the way to a MONAI Application Package. A **training bundle** is what the MONAI on-ramp *consumes*:
`configs/train.json` and friends from the Model Zoo, plus a `monai-flip.yaml` overlay (`flip/monai/`). The round trip is **not** closed: FLIP exports
inference bundles and imports training bundles, and they are different configs.
_Avoid_: bare "bundle" in this repo; always say which direction.

**SimEnv**:
The simulation execution environment (`nvflare.recipe.SimEnv`) that runs FedAvgRecipe
locally — used for integration tests and development.
_Avoid_: Direct `nvflare simulator` CLI

**FLIP()**:
The factory class (`flip.core.flip.FLIP`) that returns a `FLIPBase` implementation (Dev
or Prod) for accessing project data, the FLIP dataframe, and sending metrics to the
Central Hub.

**ScatterAndGather (deprecated)**:
Legacy NVFlare controller. Replaced by `FedAvgRecipe` + `fl.client` API.

## Relationships

- A **FedAvgRecipe** runs **client.py** (which uses the **Client API**) in a **SimEnv** (testing) or
  via `--export` + Docker compose (production)
- **client.py** uses `FLIP()` to load data before the FL loop, then trains **FLUNet** in the
  `receive → evaluate → train → send` cycle
- **Weight diff** (`TransferType.DIFF`) reduces bandwidth by sending only the model delta
  instead of full weights

## Example dialogue

> **Dev:** "Should I wrap our training in a MonaiAlgo or MonaiBundle?"
> **Domain expert:** "Depends which path you're on. Writing an app by hand? No. Write a
> `client.py` with the native Client API, use `FLIP()` to get the dataframe, build your own
> DataLoaders from `transforms.py`, call `flare.receive()` / `flare.send()` directly. Bringing in
> a Model Zoo **training bundle**? That's the on-ramp, and it's the one place we do consume bundle
> configs, but only pure-config ones, and only after they've passed the seal-time analyser."

## Flagged ambiguities

- "config.json" was used to mean both the NVFlare job config and the app
  hyperparameter file — resolved: hyperparameters are CLI arguments now, job config is
  generated by `FedAvgRecipe`
- "Executor" was used to mean both `RUN_TRAINER` (our custom executor) and any NVFlare
  executor — resolved: we use the Client API now, no custom executors
- "MONAI bundle" was used to mean both what `flip/export/` writes and what the on-ramp reads.
  Resolved: **inference bundle** (outbound, TorchScript + `inference.json`) and **training bundle**
  (inbound, `configs/train.json`). The two are not a round trip.
- Whether the on-ramp instantiates `MonaiAlgo` or drives `ConfigWorkflow` directly: open, settled
  by a 3-day spike (FLIP#1107) whose exit criterion is fewest adapter LOC and fewest MONAI-internal APIs
  touched.
